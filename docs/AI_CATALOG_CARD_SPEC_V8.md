# MAX TOUR — ТЗ: строгий parity карточек AI и каталога (v8)

## Цель

ИИ-консультант не имеет собственного дизайна экскурсионной карточки. Если рекомендация соответствует экскурсии из каталога, в AI должен использоваться **тот же DOM `.tour-card`**, который создаёт каталог, с теми же фото, пропорциями, бейджами, ценой, избранным и обработчиком `openTour(tourId)`.

ИИ отвечает за выбор `tourId` и контекст бронирования. Каталог отвечает за визуальный компонент и поведение карточки.

## Обязательные правила

1. **Только native catalog card для реальной экскурсии**
   - Старый `.ai-recommendation.ai-sales-card` является только промежуточным результатом AI и должен быть заменён на clone настоящего `.tour-card`.
   - На clone запрещено добавлять `ai-sales-card`, потому что AI CSS меняет сетку, типографику и ширину карточки.
   - Допустимы только служебные атрибуты `data-tour-id`, `data-ai-catalog-source="catalog"` и класс `ai-catalog-card-v7` для технического контроля.

2. **Одинаковая работа**
   - Клик по карточке AI выполняет тот же `openTour(tourId)`, что и каталог.
   - Like/favorite сохраняет исходный `toggleLike(...)`.
   - AI не добавляет внутрь native card отдельные кнопки «Подробнее» / «Забронировать».
   - После открытия экскурсии используется общий экран тура и общий booking flow.

3. **География должна учитывать комбинированные маршруты**
   - У экскурсии может быть несколько географических точек одновременно.
   - Пример: карточка `Дананг + Хойан` должна считаться подходящей для запроса `Я в Дананге → хочу Хойан`.
   - Нельзя определять направление только первым найденным названием города.
   - Route-policy проверяет множество мест тура (`city + region + title + searchText + tags + route`).

4. **Если AI первоначально не рекомендовал нужную карточку, но она есть в каталоге**
   - Route layer обязан найти соответствующий `tourId` в canonical `TOURS`.
   - Затем карточка создаётся через `MaxTourCatalogCardV7.createCatalogCard(...)` из настоящего catalog DOM/renderer.
   - Запрещено создавать отдельную AI-карточку для такого случая.

5. **Если готовой экскурсии в каталоге действительно нет**
   - Не показывать поддельную «карточку экскурсии».
   - Не использовать старый fallback-блок `.ai-recommendation.ai-sales-card` без фото.
   - ИИ даёт обычный текстовый ответ: маршрут доступен по запросу, затем собирает дату и состав группы и передаёт запрос дальше.
   - Цена не выдумывается.

6. **Никаких пустых и дублирующихся блоков**
   - `.ai-sales-results`, в котором все карточки скрыты, должен быть скрыт целиком.
   - Пустой блок «Подходящие экскурсии» запрещён.
   - Для одного набора рекомендаций показывается один контейнер.

7. **Booking context**
   - Перед открытием карточки из AI сохраняются `tourId`, дата, взрослые, дети, малыши и формат.
   - Далее общий booking flow использует существующий prefill.

8. **Производительность**
   - DOM observer реагирует только на добавление/удаление узлов.
   - Никаких циклов `observer → rewrite → observer`.
   - Повторная обработка карточки идемпотентна.

## Критерии приёмки

### A. Дананг → Хойан
1. Очистить AI.
2. Выбрать `Я в Дананге`.
3. Написать `Нас 2 взрослых, хотим экскурсию в Хойан`.
4. Если соответствующая экскурсия есть в каталоге, AI показывает именно native `.tour-card`.
5. Карточка содержит реальное фото и выглядит как в каталоге; текста в узкой колонке быть не должно.
6. Клик открывает тот же tour detail.

### B. Сравнение одной экскурсии
Открыть одну и ту же экскурсию из каталога и из AI. DOM/class family, фото, цена, бейджи и поведение совпадают.

### C. Нет готовой экскурсии
Если направления нет в `TOURS`, AI отвечает текстом про маршрут по запросу. Отдельная псевдо-карточка не создаётся.

### D. Пустые результаты
После геофильтрации не остаются белые пустые блоки «Подходящие экскурсии».
